# Release notes 0.261.474 – 0.261.302

[Back to release notes index]({{ '/explanation/release_notes/' | relative_url }})

### **(v0.261.474)**

#### Bug Fixes

*   **Whole-Workspace Chat Links and Reasoning**
    *   Workspace chat links can now bind one whole personal, group, or public workspace in addition to explicit document selections.
    *   Model reasoning effort is stored, shown in link previews, restored in Classic and V2, and checked again on the first send. Agent links continue to use the agent's own configured reasoning.
    *   (Ref: `functions_chat_links.py`, `chat-links.js`, `Composer.tsx`, [Create workspace chat links](https://microsoft.github.io/simplechat/guides/create-workspace-chat-links/))

*   **Model Catalog Updates Now Ship With Their Publisher Keys**
    *   Admin Settings > Model Catalog no longer warns on every deployment that the publisher verification key is not configured. The production and development publisher public keys are bundled with SimpleChat, so a deployment receives them through an ordinary upgrade; administrators have nothing to install.
    *   When the official catalog is signed with a newer publisher key, or needs a newer application version, **Check for updates** shows **Upgrade SimpleChat to get catalog updates** instead of a generic verification failure. Uploading such a package gives the same explanation, and the installed catalog keeps working meanwhile. Releases without a bundled key can now run the check and are told to upgrade.
    *   V2 no longer draws a second, unlabelled switch for `enable_model_catalog_online_updates`; **Allow online catalog update checks** is the only control.
    *   Publishers whose Key Vault cannot be reached from GitHub-hosted runners can sign with a `CATALOG_SIGNING_KEY` secret on the protected publishing environment. `scripts/publish_model_catalog.py` adds `generate-key` (local key pair, public half into the trust map, private half outside the repository) and `trust-key` (imports a Key Vault key's public half). The workflow refuses an environment that configures both a vault key and a secret, and checks that the secret matches the bundled public key before signing.
    *   (Ref: `model_catalog_package.py`, `model_catalog_updates.py`, `scripts/publish_model_catalog.py`, `.github/workflows/publish-model-catalog.yml`, `model_catalog_trusted_keys.json`, `model_catalog_development_trusted_keys.json`, `admin_settings_fields.py`, `ModelCatalogUpdates.tsx`, `model_catalog_updates.js`, `MODEL_CATALOG_PUBLISHER_KEY_SETUP_FIX.md`, [#1967](https://github.com/microsoft/simplechat/pull/1967))

### **(v0.261.473)**

#### New Features

*   **Workspace Chat Deep Links**
    *   Users can create compact `/l/<reference>` URLs that prepare a new private chat with one current agent or model, one workspace, and explicitly selected documents.
    *   Creators choose 7, 30, 90, or 365 days, or **Never expires**; 90 days is the default. Links do not grant access and are reauthorized on creation, resolution, and first send.
    *   Creators can revoke links from the chat dialog, and full Control Center administrators can list and revoke active links across the deployment in Classic or V2.
    *   (Ref: `functions_chat_links.py`, `route_chat_links.py`, `ChatLinkDialog.tsx`, [Create workspace chat links](https://microsoft.github.io/simplechat/guides/create-workspace-chat-links/), [Workspace chat deep links](https://github.com/microsoft/simplechat/blob/Development/docs/explanation/features/WORKSPACE_CHAT_DEEP_LINKS.md))

#### Bug Fixes

*   **Support Log Export Finds Its Own Sources**
    *   Support Log Export no longer asks admins to pick the Azure cloud or paste the Application Insights and App Service resource IDs. The cloud comes from `AZURE_ENVIRONMENT`, the App Service ID from App Service's own platform variables (deployment slots included), and the Application Insights ID from the new `APPLICATIONINSIGHTS_RESOURCE_ID` app setting or, when that is absent, an Azure Resource Graph lookup by the connection string's instrumentation key.
    *   "Source and storage setup" shows each resolved value and where it came from. The input fields moved under "Override detected values", where a blank field means "use the detected value"; the cloud selector only appears when `AZURE_ENVIRONMENT` cannot name a supported cloud.
    *   Saved resource IDs keep working as overrides. A previously defaulted Azure Commercial cloud no longer overrides a US Government deployment.
    *   The Bicep, Terraform and Azure CLI deployers now set `APPLICATIONINSIGHTS_RESOURCE_ID` (deployers version 1.0.40).
    *   (Ref: `support_export_discovery.py`, `support_export_contracts.py`, `support_export_service.py`, `functions_support_exports.py`, `SupportExportPanel.tsx`, `support-exports.js`, `test_admin_support_export_source_detection.py`, `SUPPORT_EXPORT_SOURCE_DETECTION_FIX.md`)

### **(v0.261.452)**

#### New Features

*   **V2 Custom Color Schemes**
    *   Administrators set the colors the modern interface uses in light mode and dark mode under Admin Settings > Appearance > Appearance. A table shows the Light and Dark value of each of eleven colors (accent, text on accent, page background, panels, borders, primary and secondary text, and four status colors), with a contrast badge on every color that carries text and live previews of both modes. A low-contrast warning suggests a nearby readable color but does not block the save. **Reset to SimpleChat default** returns to the shipped colors, and saving repaints everyone's interface.
    *   Users choose **Light**, **Dark**, **Match system** or **Custom** in Settings > Preferences > Color mode. Custom starts from the organization's colors and applies to the whole interface, with no flash of the default colors on load. The sidebar's dark mode toggle still works, and a light or dark choice made in the classic interface is still honoured.
    *   Three new switches, all on by default: **Let users create a custom color mode**, **Allow Theme Card sharing and import**, and **Require readable contrast (WCAG AA)**. With custom modes off, Custom is hidden, a saved custom mode stops applying, and the server refuses it.
    *   Every color is reduced to a plain `#RRGGBB` value on the server before it is stored, through the admin settings PATCH and the user settings route. CSS expressions, URLs, unknown color names and over-long names are refused. Contrast is judged on the ratio as displayed, to one decimal place.
    *   (Ref: `functions_color_schemes.py`, `admin_settings_fields.py`, `route_backend_users.py`, `colorScheme.ts`, `useColorSchemeRuntime.ts`, `ColorSchemeEditor.tsx`, `ColorModeCard.tsx`, `docs/explanation/features/V2_CUSTOM_COLOR_SCHEMES.md`)

*   **Theme Cards**
    *   A custom color mode can be shared as a Theme Card: a PNG with the mode's name, a stripe of its colors and a QR code drawn in those colors. **Copy as text code** gives the same thing as text. Importing reads the code stored in the PNG, or the QR code when that copy is missing (a screenshot, or an image Teams recompressed). The card is previewed with the checks it passed, and nothing changes until the user saves. Administrators can import a card into the light or dark column of the color scheme.
    *   Cards import on any SimpleChat deployment. Each carries an open checksum, so a card edited after it was made is refused, and its colors are validated again on save. The image never leaves the browser.
    *   Adds two pinned V2 dependencies: `qrcode-generator@1.4.4` and `jsqr@1.4.0`.
    *   (Ref: `themeCardImage.ts`, `ThemeCardDialogs.tsx`, `functional_tests/test_theme_card_code_format.py`)

### **(v0.261.448)**

#### New Features

*   **V2 Notifications Page**
    *   The V2 interface has a full Notifications page at `/v2/notifications`: All, Unread and Read filters, search, 10, 20 or 50 notices per page (remembered), numbered paging, **Mark all read**, refresh, and open, mark read, dismiss and acknowledge on each notice. The bell panel's footer and a new **Notifications** entry in the account menu (with the unread count) open it instead of the classic page.

    *   Workflow runs have an activity page in V2 at `/v2/workflow-activity` that takes the classic page's query (`conversationId`, `workflowId`, `runId`, `scope`, `groupId`), so every existing link maps one to one. It shows the run as a timeline with details and event history, follows a live run, cancels a run, and shows a saved Microsoft 365 email or invitation beside the run that saved it.
    *   Notifications, Latest Features shortcuts, the chat header of a workflow conversation, a workflow's run history and its header all open the V2 page. No server change was needed: the page reads the same activity routes as classic, and a regression test pins their gates to the classic page's.

    *   A custom page chosen from the V2 rail opens at `/v2/custom/<slug>` with the rail still on screen, framing a chrome-less same-origin copy (`/custom/<slug>?embed=1`) instead of leaving for the classic layout. Pages set to open in a new tab, and Python-backed pages that have not set `supports_embed = True`, keep opening in their own tab. Pages open to any signed-in user stay standalone, because those visitors cannot use V2.
    *   Only the embed response relaxes `X-Frame-Options` from `DENY` to `SAMEORIGIN` (the Content Security Policy already limits `frame-ancestors`); every other response, and Teams SSO deployments, are unchanged. The host's **Open in a new tab** opens the chrome-less document at `/custom/<slug>?embed=1`, which the classic-to-V2 redirect never sends back to V2.
    *   (Ref: `route_custom_pages.py`, `functions_custom_pages.py`, `custom_page_extension.py`, `custom_page_embed_shell.html`, `CustomPageHost.tsx`, `docs/explanation/features/V2_CUSTOM_PAGES.md`)

*   **Public Workspace Tags, Native Workspace Delete And Manage Sections For Inactive Workspaces In V2**
    *   A public workspace has a native **Tags** section: everyone who can view the workspace browses its tags, and an Owner, Admin or DocumentManager of an active workspace creates, recolours, renames, merges and deletes them.
    *   An owner deletes a group or public workspace in V2: the document count is read again at the click and at the confirmation, then the workspace is deleted and V2 returns to the group or public list. The group and public pickers no longer keep a deleted or left workspace selectable.
    *   The Owner and Admins of a locked, inactive or unrecognised-status group keep Members, Settings, Activity and Statistics in V2, as the classic manage page does. Adding a member stays closed with a read-only note. The **Manage group (classic)** and **Classic tools** buttons are gone.
    *   The Owner and Admins of a locked, inactive or unrecognised-status public workspace keep Members, Settings and Activity, and every stored role keeps Statistics. The profile and logo stay read-only, and adding members and changing roles stay closed, which is stricter than the classic page. The change-role control no longer shows in a locked public workspace, where the server refuses it.

*   **Legacy Document Upgrade In V2**
    *   The Documents explorer shows the **Update older documents** notice for personal, group and public documents that predate progress tracking, and upgrades them without leaving V2.
    *   Adds `POST /api/groups/<group_id>/documents/upgrade_legacy` and `POST /api/public-workspaces/<workspace_id>/documents/upgrade_legacy`. Each is authorized as a metadata edit on an active workspace, re-checks the role before every document, accepts no request body, upgrades at most 500 documents per request (the receipt says when more remain) and answers 207 when some could not be updated. *   **Plans Can Wait For A Quick Saved Workflow And Use Its Result**
    *   With **Wait For Quick Workflows In Chat** on, a chat plan that starts one of the user's saved personal workflows can wait for the run and use its result in the same answer, for example "run my sales digest, then compare its totals with the Q3 report in my workspace". A failed or cancelled run says so, and the steps that needed its result don't run. A run still going when the wait ends is posted to the chat by the existing post-back when it finishes.

Each check while waiting confirms that the conversation is still private and the user's, the setting is still on, and the workflow is still the user's and still quick. A failed check ends the wait and leaves delivery to the post-back's own rules.

Each run also checks again that the setting, Chat Orchestration, every step's capability, and every document, group and public workspace the plan reads are still available to that person. A refused run fails with a fixed reason before any step runs.
    *   Only steps that are safe to repeat are allowed: Search documents, Analyse documents, Compare documents, Merge documents, Inspect spreadsheets, Prepare content and Generate image. Web search, page fetches, deep research, actions, agents, workflow steps, steps that wait for a file or result, and plans that asked the user a question are refused, with a reason for each step. A run is limited to 8 steps and 15 minutes, and the schedule follows the chat-created workflow minimum interval and quota.
    *   The run inspector shows a typed result for each run: the orchestration run, each step's status, the final response and its image or file artifacts. The V2 workflow editor shows the frozen steps read-only; the name, schedule and alerts stay editable. The Classic workflow page sends these workflows to V2.
    *   A saved workflow starts with one **Run failed** alert rule, so a refused or failed scheduled run isn't missed: it sends a high-severity notification to the bell, never a pop-up, with the fixed reason. The card says so before saving, and the rule stays editable under **Alerts**.
    *   Part of #1550, refs #1543.
