# Admin connection-test reporting fix (v0.261.400)

Fixed in version: **0.261.400**

The application version is recorded in `application/single_app/config.py`.

## Issue and root causes

The V2 saved-image-model test reported a failure after successful image inference.
The shared image runner returned HTTP 200 with only a `message`, while the V2
capability picker correctly required the literal `success: true`. This was a
response-contract defect, not evidence that the saved image connection was broken.

The Key Vault permission probe passed `polling_interval` to
`SecretClient.begin_delete_secret`. The pinned `azure-keyvault-secrets==4.10.0`
client forwards that unsupported keyword to the HTTP transport, causing a
`TypeError` during cleanup. The exception bypassed the probe's structured
failure reporting, obscuring which checks had already completed and whether
its temporary secret remained.

## Technical changes

`application/single_app/route_backend_settings.py` now returns `success: true`
only after the shared image operation succeeds, and `success: false` for its
safe error responses. Existing success messages, error messages, error codes,
and HTTP status codes remain compatible. Both classic and V2 routes share
this handler. The V2 client still rejects missing, false, or non-boolean success
values; HTTP 200 alone is not proof of successful inference.

`application/single_app/functions_keyvault_test.py` calls deletion without the
unsupported keyword and uses the SDK's default polling interval. It retains
the bounded `wait(timeout=10)` and requires `done()` before reporting cleanup
success. A not-found response to the initial delete confirms that an uncertain
write left no active probe secret; a propagated polling error is instead a
cleanup failure.

Expected SDK errors, including `TypeError`, return `success: false`, the primary
failed stage, and all four `checks` outcomes. A `details` list makes the same
outcomes visible in the existing V2 connection-test component. Cleanup failure
also identifies the exact UUID-named synthetic secret using
`cleanup_secret_name` and a user-safe error message. A primary read or write
failure is preserved when cleanup also fails.

## Safety and impact

The probe deletes only the unique synthetic secret generated by that invocation.
It does not purge soft-deleted secrets, modify existing application secrets,
return probe values, expose provider exception text, or change saved settings.
Key Vault soft-delete retention still applies after successful cleanup. A cleanup
timeout means completion was not confirmed within the wait window, not that the
service necessarily rejected deletion.

These changes do not alter production Key Vault secret storage, backup encryption,
image-model bindings, or image chat behavior. No historical probe secrets are
searched for or removed.

## Validation

`functional_tests/test_key_vault_connection_permissions.py` covers list, write,
read-back and cleanup success; denied permissions; uncertain writes; mismatched
read-back; cleanup timeout; polling errors; and primary/cleanup dual failures.
Its signature-sensitive fake rejects unsupported deletion arguments. Additional
coverage runs the pinned real SDK client and poller over a signature-checked
mock `requests.Session`, including successful and failed cleanup polling.

`functional_tests/test_admin_settings_diagnostics_routes.py` exercises the real
shared dispatcher and both route adapters in normal and optimized Python.
Mocked image-operation results verify explicit success, genuine inference
failures, safe secret-resolution errors, and unchanged saved settings. Key Vault
cleanup failures retain their complete safe result through both adapters.

`ui_tests/test_admin_shared_ai_connections.py` verifies V2 image success and
rejects malformed, message-only, false-success, and HTTP-error responses.
`ui_tests/test_admin_key_vault_connection_permissions.py` verifies that V2 shows
the individual checks and exact synthetic cleanup name on partial failure.
Browser fixtures serve the real built SPA and intercept application API calls.

The scoped local validation passed 28 Key Vault functional cases, four real-route
cases spanning both import orders and Python optimization modes, seven V2 image
browser cases, and eight Key Vault browser cases. The V2 production build, all
three route-policy checks, documentation coverage, and documentation site-quality
checks also passed.

All regression coverage is local and synthetic. No live image generation,
vault operations, settings changes, or backup operations are required.

## Cold-process test diagnostics (v0.261.401)

The real-route regression still uses a fresh interpreter, both import orders,
normal and optimized Python, and its original 120-second deadline. It now emits
named wall/CPU phases and a delayed stack every 30 seconds while running. The
stack timer is canceled during interpreter exit hooks to avoid running it during
finalization.

Timeout failures retain the child's partial phase output and stacks instead of
printing the entire embedded command. An exit-hook phase helps distinguish
an import/body stall from a process-exit wait. Harness regression cases verify
that timeouts, import failures, and incomplete child runs remain failures and that
the four original command shapes and deadlines are preserved. These diagnostics
do not themselves establish the cause of an intermittent timeout.
