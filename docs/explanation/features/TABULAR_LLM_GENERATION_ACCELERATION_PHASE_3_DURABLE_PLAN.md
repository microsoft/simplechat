# Tabular LLM Generation Acceleration Phase 3 Durable Plan

Implemented in version: **0.250.139**

Associated issue: **microsoft/simplechat#1031**

## Overview

Phase 3 replaces first-batch schema authority with one bounded LLM planning call and an immutable `plan_v1.json` contract. New runs default to output-neutral shadow mode. Active mode is implemented for controlled rollout and lets batch 1 join the normal fixed-window schedule because the output schema exists before row generation starts.

## Purpose

The durable plan establishes one ordered output schema before generated rows are checkpointed. Every resume uses the same plan, and every planned output checkpoint is tied to its plan hash and source ETag. The planner defines schema only; all substantive row answers remain LLM-generated by the existing batch calls.

## Dependencies

- Durable tabular generated-output runner in `application/single_app/functions_tabular_generated_exports.py`
- Settings defaults and backend-only filtering in `application/single_app/functions_settings.py`
- Azure Blob Storage for immutable plan and output checkpoints
- Cosmos DB `tabular_export_runs` records for compact plan status and hash metadata
- Existing source authorization and version-pinned staging contracts

## Technical Specifications

### Planning Boundary

Planning runs after source staging has established the authorized source descriptor, source ETag, exact row and batch counts, model-aware batch budget, and staged input checkpoints. The planner reads no more than five rows from at most the first and last input checkpoints.

Planner input includes the user request, input column names and inferred JSON-compatible types, and shape-only sample values such as `<string:24 char(s)>`. Raw sample values are not sent in the schema sample or persisted in the plan. Oversized questions, columns, field counts, names, descriptions, and guidance fail bounded validation and use the legacy LLM schema-discovery fallback.

### Immutable Plan Contract

The validated plan is stored once with overwrite disabled at:

```text
{user_id}/{conversation_id}/generated/tabular_runs/{run_id}/plan/plan_v1.json
```

The plan contains:

- Run, source blob, source ETag, row count, and input schema identity
- Planner endpoint, model, and deployment identity
- User-question hash and requested output format
- Ordered server-owned and LLM-owned output field contracts
- JSON-compatible type and nullability for every field
- `object-v1` response protocol and prompt version
- Model-aware row, character, input-token, and output-token budgets
- Canonical SHA-256 plan hash

Only supported properties are accepted. Field names are case-insensitively unique, reserved source fields cannot be model-owned, and stored plans are revalidated against the run before use.

### Persistence and Resume

Cosmos stores `plan_blob_path`, `plan_hash`, `plan_mode`, plan status, planner model, bounded timing and token metrics, and safe failure categories. The run is marked `planning` before the provider call.

New runs also snapshot the selected chunk model and model context. Planner and row-generation calls reuse that snapshot on resume, so later administrator model-selection changes affect new runs without changing an in-progress run's model contract. Older runs without the snapshot retain their legacy resolution behavior.

- A crash after plan upload but before the Cosmos update recovers the plan from its predictable path and verifies its canonical hash.
- A crash before plan persistence falls back to existing LLM first-batch schema discovery without automatically calling the planner again.
- A ready run reloads the same immutable plan on resume.
- A missing plan, hash mismatch, source mismatch, schema mismatch, or incompatible checkpoint fails closed.
- Runs created before Phase 3 have no plan path and continue through legacy schema discovery.

### Shadow and Active Modes

`enable_tabular_generation_plan` defaults to `true`, and `tabular_generation_plan_mode` defaults to `shadow`.

Shadow mode creates and validates the plan but preserves the existing first-batch scheduling and artifact schema. After the first valid batch, the runner records exact agreement, additions, omissions, and reorderings without changing output.

Active mode applies the planned schema before the first generation window. Existing prompt and response validation require every batch to return exactly those LLM-owned fields, while the server reattaches source row order and identity. Planner timeout, provider failure, invalid response, or bounded-input rejection falls back to `object-v1` first-batch discovery for that run.

### Checkpoint Integrity

Planned output and combined-analysis checkpoints include `plan_hash` and `source_etag` blob metadata. Resume, concurrent checkpoint recovery, and final artifact assembly reject missing or mismatched metadata before accepting rows.

### Security and Privacy

Phase 3 does not change personal, group, public workspace, or chat-upload authorization. The worker still revalidates conversation ownership, group membership, public workspace visibility, source scope, and source ETag through the existing boundaries.

The plan excludes raw source rows, source values, the complete user question, credentials, and settings. Telemetry records aggregate planner counts, timings, safe failure categories, and plan identity only; it does not record model response content or field differences.

## Usage Instructions

No user workflow changes are required. New structured export and combined runs create a shadow plan automatically. Administrators can set `tabular_generation_plan_mode` to `active` after representative shadow results preserve all requested fields, or set the mode to `off` to disable planning for new runs. Runs that already contain a plan continue using that immutable contract.

## Performance Considerations

Planning input and output are bounded independently of dataset row count. Shadow mode adds one small model call but does not change current row-generation scheduling. Active mode removes the serial first-batch schema-discovery barrier while retaining the fixed-window executor used before later acceleration phases.

## Known Limitations

- Active mode requires administrator rollout after shadow agreement is acceptable.
- Phase 3 keeps the `object-v1` row response protocol. Phase 4 adds compact positional output for new active planned structured exports.
- Completion-driven checkpointing, rolling scheduling, and independent batch retries remain deferred to later phases.
