# V2 Conversation Export

## Overview

Exports a whole conversation — or several at once — from the V2 (React) interface as JSON,
Markdown or PDF, with optional AI-written intro summaries and diagrams embedded as pictures.

Before this, the V2 interface could export a *single message* as Word, PowerPoint or an email
draft, but had no way to export a conversation at all. Anyone who needed a transcript had to
switch back to the classic interface.

**Implemented in version:** 0.261.040

## Dependencies

None added. The feature reuses:

- `POST /api/conversations/export` and `POST /api/conversations/export/visual-scan`, which
  already served the classic export wizard.
- The vendored Mermaid runtime at `application/v2_ui/public/vendor/mermaid-11.17.2/`.

No backend change was required, and no new npm or CDN dependency was introduced.

## Architecture

### No new server surface

The classic wizard (`static/js/chat/chat-export.js`) already drives both endpoints, and they
are format- and packaging-agnostic. The V2 work is therefore entirely client-side, which is
also what guarantees the two interfaces produce identical files.

```
ConversationExportDialog.tsx     the stepped wizard
  ├── lib/conversationExport.ts  step list, packaging default, request assembly
  ├── lib/endpoints.ts           downloadConversationExport(), filename handling
  └── lib/exportVisuals.ts       buildConversationVisualAssets()
        └── lib/mermaidRuntime.ts  shared, hardened Mermaid rendering
```

### Why the Mermaid runtime moved

Loading, configuring and rendering Mermaid previously lived inside `MermaidDiagram.tsx`. That
works for the chat, where every diagram is a mounted component whose SVG can be read back, but
a conversation export covers messages that were **never rendered** — an old conversation, or
one that is not even open. There is no component to take an SVG from.

The runtime now lives in `lib/mermaidRuntime.ts` and both callers go through it. This mirrors
the classic interface, which separates `chat-mermaid-runtime.js` from its inline renderer for
the same reason.

The security properties travel with it: `securityLevel: 'strict'`, `htmlLabels: false`,
`suppressErrorRendering: true`, no `bindFunctions`, no icon packs, and a DOMPurify pass before
any caller writes markup to the DOM.

### Why diagrams are drawn in the browser

Mermaid is a browser library. If the client sends only conversation ids, the server has to
render every diagram itself in headless Chromium — roughly a second of browser startup per
export, producing whatever that container can draw rather than what the reader sees.

Instead the client asks the scan endpoint which diagram sources the selected conversations
contain, renders each one, and posts the PNGs back as `visual_assets`. The server matches each
asset to its fence by normalized source text and embeds the picture.

Exports use a fixed light preset rather than the reader's theme, because the file is read
outside the application, where a dark diagram on white paper is unreadable.

Failure is deliberately non-fatal. A diagram that will not render is left out, and the server
falls back to drawing it, so a broken diagram costs fidelity rather than the whole export.

### Model identity

An intro summary is generated by a model, and a model is **not** identified by its deployment
name alone. When `enable_multi_model_endpoints` is on, the same deployment name can exist on
several endpoints. Sending only `summary_model_deployment` makes the server's resolver return
nothing and silently fall back to the legacy single-endpoint client — a different endpoint from
the one the user picked, with no error surfaced anywhere.

`summaryModelFields()` therefore reuses the composer's own `modelIdentityForSelection()` mapping
and remaps its output onto the `summary_*` names:

| Composer field | Export field |
|---|---|
| `model_deployment` | `summary_model_deployment` |
| `model_endpoint_id` | `summary_model_endpoint_id` |
| `model_id` | `summary_model_id` |
| `model_provider` | `summary_model_provider` |

All four are nulled when no intro was requested, so the request always describes what the user
actually chose.

## Configuration

None. The feature is always available in the V2 interface and has no settings key.

## Usage

### Exporting one conversation

1. Hover a conversation in the left rail and open its **⋯** menu.
2. Choose **Export**.
3. Pick a format, then packaging, then whether to include an intro summary.
4. Review the summary and choose **Download**.

The same wizard is available from the **Export** button in the conversation details dialog.

### Exporting several conversations

1. Choose **Select** above the conversation list.
2. Tick the conversations to include, or use **All**.
3. Choose **Export**.
4. Step 1 lists what was selected so any of them can be removed before continuing.

Selection mode ends once an export is started.

### Choices

| Step | Options | Notes |
|---|---|---|
| Format | JSON, Markdown, PDF | JSON keeps the original markdown, so its diagrams stay as source |
| Packaging | Single file, ZIP archive | Defaults to ZIP when more than one conversation is selected |
| Summary | Off, or on with a model | One intro is written per conversation, so a large export takes longer |

The download is named by the server, so a V2 export and a classic export of the same
conversation produce the same filename.

### Fixed along the way

`svgRaster.ts` read a percentage width as a number. Mermaid emits `width="100%"` with no height
attribute when `useMaxWidth` is on, so `parseFloat("100%")` returned `100` and a 1094×541 diagram
was rasterized into a 100-pixel sliver. A percentage now reports no size, so the viewBox is used
instead. This also affected the existing per-diagram PNG download in the chat.

### Why the dialog is portalled

The wizard renders through `createPortal` to `document.body`. The conversation rail lives inside
the sidebar's `.glass` element, and a non-`none` `backdrop-filter` makes an element a containing
block for fixed-position descendants. Rendered in place, the dialog's `fixed inset-0` resolved
against the 280px sidebar instead of the viewport, drawing the wizard as a narrow column whose
backdrop dimmed only the rail.

## Known limitations

- Per-diagram colour overrides are not applied to exported diagrams. Overrides are addressed by
  a block's position within one message, which a whole-conversation export has no reliable way
  to resolve, so exports use the neutral preset.
- At most 60 diagrams per export are rasterized in the browser, matching the server's
  `EXPORT_VISUAL_ASSET_MAX_COUNT`. Any beyond that are drawn server-side.
- **All** selects the conversations currently loaded in the rail, not every conversation that
  exists; the list pages as it is scrolled.
